# #168 现状：双容量指派已实现，但**不可行实例会搁浅行**，且太慢

## 已实现

`model/two_sided.py`：全局每码容量 `q_k = ⌊B/K⌋`（前 `B mod K` 个码 +1）与每个父前缀的同码上限 `r_g = ⌈n_g/K⌉` **同时生效**；按 `plan_ik` 降序访问码，逐码在「全局余量」与「该父前缀尚未用此码」的双重约束下取行；剩余行在双约束内按代价最小补齐；`relaxations` 记录放宽次数；`ROUNDING_OFF` 退回 `argmin`。层级规则已切到 `two_sided.assign`。

## 实测（`tests/test_two_sided.py`）

- **4 通过**：无父时全局容量**恰好**成立（1024 行/256 码 → 每码 4）；`ROUNDING_OFF` 与 `argmin` 逐位一致；偏斜计划下全局容量仍封顶（这正是 #167 缺的约束）；负载可行实例上 `relaxations == []`。
- **1 失败**：`test_both_bounds_hold_with_parents`（512 行、64 码、64 个父组，每组 8 行；每码应为 8 行、每组内每码 ≤1）。实际分布不等于 8 —— 说明该实例下"逐码取最想要的行 + 每组每码 ≤1"的贪心会**搁浅部分行**（它们落到 `cost.argmin` 兜底，破坏容量恒等式）。Issue 要求放宽次数 = 0，而这里的失败正是"贪心不可行"的形态。
- **速度**：整套测试 193 s（单个带父组的用例就占了大部分）——导出规模（24587 行）下按现在的内层 Python 循环会远超 Issue 的 60 s 上限。

## 结论与下一步（都不需要新决定）

实现方向对（两侧约束都在），但算法不完整：搁浅行需要**增广/重指派**（例如按组内剩余容量做一次二部匹配或迭代修复），并把「逐码选行」的内层循环向量化。未派发、未跑任何 Stage2。

## 诊断（本轮）：容量计数被多记了一行

在 512 行 / 64 码 / 64 组（每组 8 行）的实例上直接插桩：

| 量 | 实测 |
|---|---|
| 超容量码 | 码 10：**9 行**（容量 8） |
| 各父组内不同码数（前 5 组） | 8 / 8 / 8 / 8 / 8（父前缀上限成立） |
| `relaxations` | **1** |

即：父前缀上限是对的、总行数也是对的（512），但**有一个码多拿了一行、另一个码少一行**，并触发了 1 次放宽。把兜底从 `cost.argmin` 改成"优先用有余量的码"之后仍然如此，说明多记发生在**主循环的容量账本**（`used_global` 自增）与最终 `picks` 之间，而不是兜底分支。

下一步（明确的修法，无需新决定）：不要维护自增账本，改为**从 `picks` 现算**每个码的计数再判定余量（`used = bincount(picks, minlength=K)`），这样账本与结果不可能不一致；随后对仍然搁浅的行做一次按组的重指派（组内换码）。同时把内层 Python 循环向量化以满足 60 s 上限。
