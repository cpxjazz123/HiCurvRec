## C12 首轮执行：基线的导出 SID **不能**从它的 checkpoint 复现（115/73,761 码不一致）

按 §1「从 checkpoint 重新编码全部商品并逐项核对导出 SID」执行，脚本 `analysis_sid_recall/sid_reencode.py`，回放走**基线自己的** `model/layers.MLP`（严格 `load_state_dict`），随后按 baseline 的 `argmin` 规则三级取码。

**对象**：`results/stage2_RQ-VAE/TIGER_RQ-VAE`
- checkpoint `af8efc29…97a8`
- 导出数组 `sids_for_hgrec.npy` `6f2682c1…07c2`（Stage3 读的就是它）
- `item_sids.json` `025ad8bd…0059`

**结果**

| 项 | 值 |
|---|---:|
| 商品数 | 24,587 |
| 不一致码数 | **115**（L1 4 / L2 24 / L3 87） |
| 受影响商品 | **90** |

**为什么不是"去碰撞列"造成的**：`_extend_collisions` 写的是 `result[i, :-1] = row` 与 `result[i, -1] = 768 + occurrence`，因此前 3 列必然等于训练时的原始码；计数器只出现在第 4 列（实测第 4 列取值 768–780）。所以这 115 个码的差异只能来自"导出时编码器前向与此刻回放不同"。

**不一致商品全部落在 1,827 个重码组内**（回放重码组数 1,827），且每个组内都有一条记录的第 4 列 = 768 + 序号 —— 与 `_extend_collisions` 的分组顺序完全一致。也就是说：**第 4 列是按回放能算出的码分组的，前 3 列却在同组内不同**。这两件事不可能同时成立，说明导出时那一次前向的浮点结果与现在回放不同。

**候选解释（未验证完，按顺序排查）**

1. 导出发生在训练进程内、`model.eval()` 之后但同一 CUDA 会话，而这里在 CPU 上回放；L3 最近邻间隔最小组只有 5e-6（见下），足以翻转。
2. 导出用的是 DDP 包裹后的模块（`raw_module = model.module`），BN/Dropout 状态与 `eval()` 的调用顺序需要逐步对齐。
3. 训练脚本里 `init_codebook` 之后的码本与 checkpoint 保存时刻之间若有任何 in-place 更新，回放会与导出不同。

**对 §5 的影响**：Δ 由前三个码计算，115 个码（0.16%）不太可能改变 Δ 的符号，但 §1 要求"逐项核对"到 0 不一致才算通过；在解释清楚之前不能声称该基线的 SID 可信，也就不能用它做 C14 的基线 Δ。

**最可疑的具体点**：以下五个不一致商品在 L3 的最近与次近码字距离差只有 5e-6 量级

```
item 1700: level-3 margins 0.02589972 vs 0.02594152 (Δ=4.2e-5)
item 1484: 0.02522282 vs 0.02523505
item 1377: 0.04481864 vs 0.04482312
item 704 : 0.07249615 vs 0.07250107
```

也就是说这些码在数值上位于决策边界上，任何前向差异（CPU vs GPU）都会把它们翻过去。**下一步**：把回放改到 GPU 并在 `torch.no_grad()` + `eval()` 下逐层对齐，若仍不一致再对比导出时刻的 `raw_tokens` 中间量。
