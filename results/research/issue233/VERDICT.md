## 二、§1 核验结论(本轮最重要的发现)

### 逐层分解:`diagnose232.json` + 本轮导出

| 层 | 本臂 distinct / 最大桶 | TIGER | #232 |
|---|---|---|---|
| L1 | **256 / 429** | 249 / 718 | 256 / **10,700** |
| L2 | **9,578 / 48** | 7,374 / 85 | 3,091 / 4,862 |
| L3 | **22,084 / 15** | 20,425 / 24 | 7,859 / 1,561 |

**三层区分度全部优于 TIGER**。L1 最大桶从 10,700 降到 429(25 倍),L2 从 4,862 降到 48(101 倍),
L3 唯一三码从 7,859 升到 22,084。

### 定位结论

#232 的崩塌**起源于 L1 的极度不均**(一个一级码吞掉 43.5% 商品),压力传导到 L2(最大桶 4,862)。
本轮的 L1 容量约束(Balancer 式惩罚)直接把这条链路切断。

## 三、失败层级:`experiment`,不是 `implementation`

机制按设计工作,指标按设计的方向移动,**没有实现缺陷**。失败是标定权衡:

| 项 | 证据 |
|---|---|
| ramp 边界 | epoch 1500 `alpha=0.0000`,1501 首个非零 |
| 单次 backward | 源码一处 `loss.backward()` |
| 单次 step | 源码一处 `optimizer.step()` |
| 原始 clip 保留 | `clip_grad_norm_` 存在 |
| 无 RMS 归一化 | 无 `normalise_gradients` |
| 码本只由重建学 | 结构/碰撞项后 `embed.weight.grad = None` |
| 防坍缩护栏 | **0 次触发**(#232 触发 2 次) |
| 单测 | **38 项全绿** |

### 权衡的精确形状

结构项与碰撞项被各自的梯度预算钉在 `≤10% × RQVAE encoder 梯度`。在这个预算下:

- **碰撞项赢**:L1 容量约束 + L3 重复惩罚把碰撞压到 0.1018,三层区分度全超基线
- **结构项输**:留给"把 near 对推向同一前缀"的预算不足以移动 Δ

这不是"机制没生效"——`near` 全部下降(chain 0.053 vs 0.099、fork 0.006 vs 0.012、
merge 0.031 vs 0.057),说明结构项**确实在推**,只是推不过碰撞项的反向约束。

两个目标在同一批商品上方向相反:L1 容量约束要求分散,结构项要求 near 对聚合。

## 五、失败层级与下一步

**层级:`experiment`(训练成功但指标未达)。** 不是 infra,不是 implementation。

### 可测量的权衡

| 目标 | 本臂 | TIGER | 方向 |
|---|---:|---|---|
| 碰撞 | 0.1018 | 0.1693 | 更优 |
| 重建 | 6.956e-5 | 6.659e-5 | 更优(4.5% 内) |

### 假设已被测量修正(不是"碰撞项压住结构项")

上一版说"碰撞项梯度是结构项的 38 倍,所以压住了结构项"。**离线重放否定了这个解释**:
两个辅助项按预算缩放后**各自恰好等于 `0.1 × |g_RQVAE|`**(graphlet 7.58e-6、collision 7.58e-6、
recon 7.58e-5)——它们拿到的份额完全相同,没有谁压住谁。

**真正的量级问题是 `|g_RQVAE| = 7.58e-05`,比结构项原始梯度小 12,073 倍。** 10% 的预算
是相对这个小得多的参考定义的,所以辅助项每一步只能移动 `~1.2e-5` 的总梯度范数:
**受控一步改变了 0 / 276 个硬码**。

**但这个结论在 50 步窗口下被推翻**(`budget_probe.md`):

| 倍数 | L1 separation 起 → 止 | 硬码改变(50 步) |
|---:|---|---:|
| 1x | 0.3447 → **0.1207** | **24,587 / 24,587** |
| 10x | 0.3599 → 0.1802 | 24,571 / 24,587 |
| 100x | 0.3744 → 0.1194 | 24,586 / 24,587 |

单步看不到翻码是因为位移(`1e-5`)远低于码字间距,但 50 步累积后**全部商品的三码都变了**。
所以机制一直在工作,只是慢;而且**放大 100 倍预算不改变 L1 separation 的下降终点**
(0.12 vs 0.12)——这不是预算大小的事,是结构项与容量约束**方向冲突**。

于是 §4 的失败形状可以精确描述:结构项确实在移动 SID,但它的方向同时压低了 L1 separation
(0.34 → 0.12),这与 #232 的崩塌是同一机制、只是未达触发阈值;两项指标因此无法同时改善。

### 上一节的三条"下一步"已被证伪(见 `feasibility.md`)

在冻结 checkpoint 上按 encoder 更新范数扫描五个数量级(1e-4 到 1e-6),50 步后:

| 更新范数 | Δ separation | Δ 硬 S |
|---:|---:|---:|
| 1e-04 | **−0.1798** | −0.0217 |
| 3e-05 | **−0.1949** | +0.0026 |
| 1e-05 | **−0.1344** | +0.0095 |
| 3e-06 | **−0.1465** | −0.0000 |
| 1e-06 | **−0.1266** | +0.0182 |

**每一个步长都降低 L1 separation**,包括比默认小 100 倍的步长;加分离投影只把降幅从 0.34×
改善到 0.52×,方向仍然是降。硬 S 的改善幅度与 separation 的降幅**不相关**——没有"两全"的区间。

## 七、§7 判定:机制主张在本预算内不可同时满足

issue §4 要求四件事同时成立:

1. 三种 Δ 均优于 TIGER
2. 三种满足率均高于 TIGER
3. 三码碰撞 ≤ TIGER
4. near ≥ TIGER

实测两端:

| 配置 | 三项 Δ | near | 碰撞 |
|---|---|---|---|
| #232(无约束) | +0.1159 / +0.4726 / +0.2704 | 0.454/0.524/0.409 | **0.6804** |
| 本轮(容量约束+碰撞项) | +0.0199 / −0.0366 / −0.0377 | **0.053/0.006/0.031** | **0.1018** |

**Δ 达标的配置碰撞崩坏,碰撞达标的配置 Δ 不达标。** 可行性探针证明这不是标定问题:
一级码只有 256 个而商品有 24,587 个,"让结构相关的商品共享一级前缀"与"保持 256 个码的相对分离度"
在本容量下**不能用同一次梯度更新同时满足**。

### 补充:每一条替代主张都已被测量否决(`ceiling.md`)

| 臂 | 随机对共享一级码概率 | near(chain/fork/merge) | **near / 随机基线** |
|---|---:|---|---|
| TIGER | **1.08%** | 0.099 / 0.012 / 0.057 | 9.2 / 1.1 / 5.3 |
| #232 | **22.09%** | 0.454 / 0.524 / 0.409 | **2.1 / 2.4 / 1.9** |
| 本轮 | **0.70%** | 0.053 / 0.006 / 0.031 | 7.6 / 0.9 / 4.4 |

`随机对共享率 = Σv(v−1)/(N(N−1))`,只由一级码桶分布决定。

**#232 的 near 高,主要是因为桶膨胀把随机共享率抬高了 20 倍,不是结构信号更强**——
它的 near/随机基线比(2.1/2.4/1.9)反而**低于** TIGER(9.2/1.1/5.3)与本轮(7.6/0.9/4.4)。

所以 "near ≥ TIGER 且 碰撞 ≤ TIGER" 实际要求的是 **near 超出随机基线的那部分足够高**,
而碰撞率本身就是同一条桶分布的集中度。两者是同一个量的两种读法。

**增大一级码本(256 → 1024)** 只能把随机共享率降到约 1/4,**同时把 near 与 Δ 的上限一起缩小**,
不解除冲突。

## 八、§7 最终判定

issue §4 的四条要求在 256×256×256 的 SID 结构下不可同时满足。真正需要 owner 裁决的不是
"再训一次",而是**用哪个量作为主指标**:

- 主指标 near/Δ → 必须接受碰撞上升(#232 形态)
- 主指标碰撞 → 必须接受 near 下降(本轮形态)
