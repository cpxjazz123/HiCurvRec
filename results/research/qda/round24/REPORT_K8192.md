# 冻结 batch 下的 `K > batch`:8192 码字 / 4096 商品

我上一轮写"冻结配方规模下的 K > batch 需要 8192 簇 KMeans,不为它消耗预算"。**这个理由错了**:实测 24587×32 上 8192 簇 KMeans 只要 **21.3 秒**(256 簇 0.9 s、2048 簇 4.7 s)。于是跑掉。

## 设置

`CODEBOOK_SIZE = [8192, 256, 64]`,**冻结 batch 4096**,30 epoch。L1: 4096 商品 < 8192 码字 → 轮转区。

## 结果:跑通,而且该层 8192 个码字全部用上

```
epoch=30  raw_unique=15666/24587  collision=0.362834  0.93 s/epoch
产物审计: PASS  levels 8192/256/64
CodebookCollapse: 0 次
```

- **零拒绝**:轮转分配、间距检查、重复检查在 8192 码的规模下都正常。
- **L1 的 8192 个码字全部出现在导出里** —— 轮转下界是 ⌈8192/4096⌉ = 2 步,实际跑了 180 步。
- 碰撞 0.3628 是 **30 epoch 的欠训练**结果,不是质量结论。

## 这一轮修正了两件事

1. **成本估计**:8192 簇 KMeans 21 秒,不是"消耗不起"。之前的拒绝该撤回。
2. **检查的内存/时间**:K=8192 下去重 17.9 ms、间距 110 ms(分块),整 epoch 0.93 s —— 可用。

## 覆盖边界(现在没有"未运行"的机制 regime)

| regime | 规模 | 结果 |
|---|---|---|
| 可行区 | 3000 epoch,256 码 | 零拒绝,死码 0 |
| 轮转区 | 10 epoch,batch 256 / 512 码 | 零拒绝,512 全用 |
| **轮转区(冻结 batch)** | **30 epoch,batch 4096 / 8192 码** | **零拒绝,8192 全用** |
