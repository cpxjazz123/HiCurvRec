# 守卫在它没被调过的机制形态上:变了什么、没变什么

此前所有运行都在 `K=256/256/256、D=32` 上。一个"任何机制"的断言必须说明:**当机制改变码本容量或维度时还成不成立**。这轮用两个新形态实测。

## 形态 A:每层不同码本容量 `[512, 256, 64]`

| | |
|---|---|
| epoch | 60 / 60,**零拒绝** |
| 每级使用码字 | **512 / 256 / 64**(全用满) |
| 三级码碰撞率 | 0.056412 |
| 产物审计 | PASS,gate allowed |
| 每 epoch | ~0.15 s |

L1 的 512 个码字与 L3 的 64 个码字都由同一套检查正确处理 —— 守卫的 K 来自代价矩阵与码本本身,不写死。

## 形态 B:码本维度 `D=16`(原 32)

| | |
|---|---|
| epoch | 60 / 60,**零拒绝** |
| 每级使用码字 | 256 / 256 / 256 |
| 三级码碰撞率 | 0.044007 |
| 产物审计 | PASS,gate allowed |

编码器输出、码本、量化都缩到 16 维,守卫的距离/间距判据按实际张量计算,无需改动。

## 这说明什么、不说明什么

**说明**:守卫不依赖固定的码字数或维度,也不依赖上一轮已验证的"分配规则"(argmin / Sinkhorn 输出)。它读取的是**那张代价矩阵和那张码本**本身。

**不说明**:它不覆盖软量化(无离散索引)与 `K > batch` —— 这两类仍按设计**拒绝准入**。
