# #175 DUL 复现：实现与测试（派发前状态）

## 实现

- 新树 `TIGER_dul_rq`（`DUL`），从**冻结基线**复制：量化、残差递推、Sinkhorn（ε=0.003、50 sweeps、centring）、读出、导出逐字节未改；#171–#174 的双容量/行优先/增广/软容量代码**均未带入**。
- `model/unique_loss.py`：`L_unique = mean over P of relu(cos(z_i,z_j) − m)`，`P` = 同一 batch 内三级码完全相同且商品不同的行对（`collision_pairs` 按三元组键分组），`z` 为**量化前**连续表示，三级码 `detach`；`BETA_UNIQUE=2.0`、`MARGIN=0.9`（论文值，不调）；`UNIQUE_OFF` / `PAIR_SOURCE_OFF` / 出厂三态。
- 接线：`MixedRQVAE.forward` 在 `self.rq(encoded)` 之后计算并加到 `quant_loss` 上，因此 `L = L_RQ + 2.0·L_unique`，无需改 trainer 的损失装配。
- 每 batch 记录 `|P|`、`cos>m` 对数、`L_unique`（`LAST_STATS`），并在评估 epoch 写进 `training_metrics.jsonl` 的 `unique_pairs` / `unique_above_margin` / `unique_loss` 与打印行。
- 方向性矛盾已写进模块 docstring：按公式 `m` 越大越**宽松**（`cos ≤ m` 即零损失），与论文正文表述相反；**照公式实现**。

## 首次正式运行的中断与观察（记在案）

- 运行到 epoch 400 时发现评估记录里 `unique_pairs` / `unique_loss` 为 **None**：`from model.unique_loss import LAST_STATS as UNIQUE_STATS` 绑定的是**当时的空 dict 对象**，而 `uniqueness_loss` 里 `global LAST_STATS` 会**重新绑定**模块属性，别名因此永远看不到更新。已改为通过模块读取（`unique_loss_module.LAST_STATS`，`d795f030` 之后的又一处）。
- 该缺陷只影响记录、不影响损失；但 Issue 第 5 条要求逐 batch 记 `|P|` 与 `cos>m` 占比，故按执行故障重启这一次运行（机制未变、未调 β/m）。
- 中断前的碰撞轨迹值得记：eval **300 → 0.67194**、**350 → 0.59649**、**400 → 0.56957**，即 DUL 在跑，但三级碰撞率远高于基线 **0.162444**、且高于 §89 的 **0.40** 门槛（趋势向好，但离门槛仍远）。

## 重启后的首批记录（epoch 150，统计已生效）

| 量 | 实测 |
|---|---|
| `|P|`（评估 batch 内同码行对） | **275** |
| 其中 `cos > m`（m=0.9）的对 | **1** |
| `L_unique` | **2.0e-4** |
| 三级碰撞率（全量导出） | **0.714483** |

两点必须并列陈述：

1. **DUL 项几乎完全饱和**：275 对里只有 1 对余弦超过 0.9，`L_unique ≈ 2e-4`，相对 `L_RQ`（1e-4 量级）虽不小、但梯度只来自那 1 对。这正是公式方向的直接后果——`m = 0.9` 在 `relu(cos − m)` 里是**很宽松**的阈值（只有几乎同向的对才被罚），与论文正文"越大越严格"的描述相反；Issue 要求照公式实现并记录该矛盾，此处即为实证。
2. **碰撞率 0.714 ≫ 基线 0.162444**（且远高于 §89 的 0.40）：本臂目前把三级碰撞显著推高了。中断前那次运行的轨迹（0.672 → 0.596 → 0.570）显示它在缓慢改善，但起点比基线差得多。
