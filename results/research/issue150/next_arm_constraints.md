# 结构先验边际路线的修正定义（#150 根因分析的结论，供下一臂开局使用）

来源：ISSUE_CONTROLLER 对 #150 的根因审查（2026-11-10T12:26Z）。#150 本身不重跑、不改常量
重训（§19g）：碰撞 0.68215 ≥ 0.40，Stage3 未启动，负结果留档。以下六条是对这条路线本身的修正。

## 根因（实测）

1. **目标与被约束量同源，且每 epoch 重排**：`usage_partition` 按 run 自身的 `usage_running` 给桶，
   `set_marginal` 每 epoch 重调；用得多的码下轮进大份额桶、继续被鼓励，用得少的更易被放弃。
   方向反了的证据：`bucket_mass [8532, 6622, 6968, 2434]` 对目标 `[5913, 6164, 9263, 3216]`，
   份额最大的桶欠配 25%，两个小份额桶超配 44% / 7%。
2. **把列边际施加在无法实现它的层级**：只有末级有 Sinkhorn；一、二层是 `argmin`，要让使用分布
   贴近 2.88× 跨度的非均匀目标，只能扭曲码本几何 —— 坍缩就发生在这里。实测一、二层末轮只剩
   58 码、单码 58.7%、归一化熵 0.258（epoch 1000 还有 172 码 / 15.9%）。
3. **没有独立的曝光护栏**：训练中无边界，坍缩只在事后报告里被看见。

## 下一臂必须满足（逐条）

1. 桶划分在整个 run 内**冻结**，只由训练集统计（τ，或未训练前向一次的码-结构层亲和度）决定一次，
   写盘并记 SHA-256；禁止用 run 自身的 usage 重排，`set_marginal` 不再每 epoch 改 partition。
2. π 只作用于**末级**（Sinkhorn 均衡分配）；一、二层保持基线 `argmin` 且不加 usage/KL 约束。
   若要约束一、二层，须先单独提出"在一、二层改用 Sinkhorn"这一研究问题并获批准。
3. 每个评估 epoch 检查逐层 `codes_used`、`max_bucket_share`、归一化熵；`max_bucket_share > 10%`
   或 `codes_used < 128` 即判机制失效，按 FAIL 停止，不跑满 3000 epoch。
4. 派发前先证明边际可实现：在冻结 batch 上，于施加边际的层级测实现列质量对 π 的相对误差 ≤ 5%。
5. 逐层记录 `L_prior` 的 KL 与 target-vs-realized 比值（不得只记平均）。
6. 新 Issue 以本文件为开局定义，并注明与 #150 的差异：冻结桶 + 只在末级施加 + 曝光护栏。
